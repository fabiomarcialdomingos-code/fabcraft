# fabcraft v1 — design spec

**Status:** draft, awaiting review
**Date:** 2026-10-12
**Owner:** fabiomarcialdomingos-code (10-year CAD draftsman; sees the real drafting pain this
targets — see project context below)

## 1. What fabcraft is

fabcraft is a new, standalone CAD product for generating **manufacturing/production drawings
automatically**, built on top of cadcraft. It is conceptually inspired by the real commercial
product **TecnoMETAL** (Steel & Graphics, runs on BricsCAD — auto-generates production drawings,
BOM, weld lists, connection tables, nesting and CAM/NC output from a structural-steel model), but
is a **clean-room, independent implementation**: no code, UI, icons, file formats or text from
TecnoMETAL or any other commercial CAD is read, copied, or reverse-engineered. Only the observable
behaviour/concept is a reference point — the same relationship cadcraft already holds with AutoCAD.

The core problem fabcraft v1 solves: **dimensioning and view layout are the biggest time sinks for
CAD draftsmen** producing shop/fabrication drawings. The target user already knows how to draw a
part (2D, 3D or an assembly); fabcraft's job starts the moment that part exists and turns it into a
fully dimensioned, shop-ready drawing with one command, without taking away the draftsman's freedom
to draw however they want.

## 2. Repository and reuse strategy

- New, independent repository: `https://github.com/fabiomarcialdomingos-code/fabcraft` (already
  created, empty, default branch `main`). Not part of the `storytold` org.
- `fabcraft`'s Cargo workspace (`crates/*`, `apps/*`, `xtask`, mirroring cadcraft's layout) declares
  **all** of cadcraft's crates as git dependencies pinned to a specific rev of
  `storytold/cadcraft` (`cadcraft-geom`, `-dxf`, `-dwg`, `-color`, `-doc`, `-constraints`, `-fonts`,
  `-render`, `-io`, `-engine`, `-ui-egui`, `-mcp`) — the same pattern cadcraft itself already uses
  for `craft-ui`. This inherits the entire CAD (drawing, dimensions, blocks, hatch, layouts,
  plotting, DXF/DWG I/O, the egui UI, MCP control) with no rewrite. Bumping the pinned rev is how
  fabcraft pulls in cadcraft's future fixes and features.
- fabcraft-specific work lives in new crates built *on top of* cadcraft's crates, never inside them:
  - `crates/fab-engine` — the fabrication domain: `PartData` model, the smart drawing commands, the
    automatic dimensioning engine, the hole-table/BOM generation, the sheet auto-layout algorithm.
  - `crates/fab-ui` (only if needed) — fabrication-specific panels, reusing `cadcraft-ui-egui`'s
    `theme::Tokens` and UI conventions.
  - `apps/fabcraft` — wires everything together the way `apps/cadcraft` does today, registering the
    additional fabrication commands alongside cadcraft's existing ones.
- All of cadcraft's non-negotiables carry over unchanged: never-crash (`unsafe_code = "forbid"`,
  no `unwrap`/`expect`/`panic!`, `catch_unwind` guard at the top level), "everything is a command"
  (`CommandSpec` with JSON form + optional interactive prompt), programmatic calls never open
  dialogs, layering discipline, clean-room.

## 3. Part data model

A **Part** is any drawn object that fabcraft's fabrication pipeline understands structurally
(what kind of stock it is, its dimensions, material, and anything the automatic dimensioning engine
needs). Two ways a piece of geometry becomes a Part:

1. **Smart tools** (preferred path): dedicated draw commands — `plate`, `profile` (catalog-backed
   or free), `tube`, `bent-profile` — that draw the geometry (reusing cadcraft's existing
   `LINE`/`PLINE`/`CIRCLE` primitives underneath) **and**, in the same atomic command, attach the
   Part data. No extra step, no imposed workflow change for the draftsman who uses them.
2. **Freehand geometry** (always available, never restricted): plain `LINE`, `PLINE`, `CIRCLE` etc.
   stay exactly as they are in cadcraft today. When the draftsman invokes the automatic dimensioning
   command (`fabdim`, see §5) on geometry that has no Part data yet, fabcraft asks **one** question
   (kind + the same fields the smart tools would have filled in) before proceeding. After that, the
   rest of the pipeline is identical regardless of which path created the Part.

**Storage (v1 decision): blocks + attributes.** A Part is stored as a cadcraft block instance whose
attributes carry the structured fields (`Kind`, `Thickness`, `Material`, `ProfileCatalogRef`, ...).
This reuses cadcraft's existing block/attribute infrastructure (BATTMAN, ATTSYNC, attribute data
extraction) directly, and — unlike an app-private XDATA/extension-dictionary approach — the data
stays readable as plain block attributes by any other DXF/DWG-reading CAD, not locked inside
fabcraft.

**Internal representation is decoupled from storage.** `fab-engine` exposes a `PartData` struct
(`PartKind::Plate { thickness }`, `::Profile { catalog_ref: Option<ProfileRef> }`, `::Tube { .. }`,
`::BentProfile { .. }`, `::Unclassified`) that every downstream consumer (dimensioning, hole table,
layout) reads. `PartData` is *populated from* block attributes in v1, but nothing downstream reads
attributes directly — so switching the storage mechanism later (e.g. to XDATA, approach B discussed
during design) only requires rewriting the populate/persist functions, not the consumers. This is a
deliberate design constraint, not a nice-to-have: the user explicitly asked to start with the
attribute approach while keeping the door open to change it.

**Profile catalog**: a table of standard structural profile dimensions (W/I/H/U/L sections, tubes)
sourced from public engineering standards and published manufacturer dimension tables (e.g. ABNT
NBR), never copied from any commercial CAD's bundled library. A `profile` command always offers a
"free" option that bypasses the catalog entirely and lets the draftsman draw the section by hand;
the catalog exists to save time, not to gate what can be drawn.

## 4. Smart drawing commands (fab-engine)

New `CommandSpec`s, following cadcraft's existing command conventions exactly:

| id | Label | Behaviour |
|---|---|---|
| `plate` | Desenhar Chapa | Draws a closed profile (reuses `PLINE`); prompts/accepts thickness + material; stores `PartKind::Plate`. |
| `profile` | Desenhar Perfil | Either places a catalog profile (pick from the public profile table) or draws free (`PartKind::Profile`, `catalog_ref: None`). |
| `tube` | Desenhar Tubo | Places a tube section (round or rectangular hollow section) from the catalog or free; stores `PartKind::Tube`. |
| `bent-profile` | Desenhar Perfil Dobrado | Draws a sheet-metal part with one or more bend lines; stores bend angles/radii needed for flat-pattern calculation; `PartKind::BentProfile`. |

Each command runs through the JSON form with explicit params and no dialog (per "programmatic
calls never open dialogs"); interactive/menu invocation prompts for the missing fields.

## 5. Automatic dimensioning engine

Single orchestrating command: `fabdim` (label: "Cotar Desenho"). Given a selection of one or more
Parts (classifying freehand geometry first if needed, per §3), it:

1. Generates the views required for the Part's kind (see table below).
2. Places dimensions and callouts using a **per-kind template** (not a generic silhouette-analysis
   algorithm — rejected for v1 as one of the hardest unsolved problems in CAD automation; templates
   cover the overwhelming majority of real shop parts and are far faster to deliver correctly).
3. Builds a hole table (cadcraft's existing Table feature) when the Part has holes: columns for
   label, diameter, X, Y relative to a reference corner/datum.
4. Runs the sheet auto-layout algorithm (§6) to place everything on a generated Layout.

All dimensions fabcraft creates are real cadcraft dimension entities bound to the actual geometry's
definition points — never disconnected lines drawn on top. This is the literal mechanism behind the
"com lastro" (grounded/traceable) requirement: if the underlying geometry changes, the dimension
updates, exactly like a manually-placed cadcraft dimension would.

| PartKind | Views generated (v1) | Dimensions/callouts |
|---|---|---|
| Plate | 1 (the flat outline, as drawn) | Overall width/height, thickness callout, hole table |
| Profile / Tube | 2 (elevation along the axis + end cross-section) | Overall length, cross-section callout (catalog name or free-section geometry), hole table along the axis |
| Bent profile | Flat/unfolded pattern view **and** the folded/formed view | Flat-pattern dimensions, bend angle/radius callouts per bend line, hole table |

**Known highest-risk item:** the bent-profile flat pattern requires a bend-allowance (K-factor)
calculation to convert the folded geometry into its true flat development. This is a standard,
publicly documented sheet-metal engineering formula (not proprietary to any vendor) — safe to
implement clean-room — but it is real engineering/geometry work, the single riskiest piece of the
v1 scope, and should get the most test coverage (reference values from published formulas, not
guessed).

## 6. Sheet auto-layout ("hero" sizing)

After views/dimensions/tables exist (still at the real-world 1:1 model scale), a separate step
decides how to present them on paper:

1. Compute the bounding box of everything that needs to appear (views + dimensions + hole table +
   callouts).
2. Pick the **smallest sheet size** from a configurable size range (e.g. A4 → A1) at which a
   configurable minimum legibility threshold is met (e.g. dimension text never renders below N mm
   when plotted) — not a fixed engineering scale ratio, not a fixed paper size.
3. Generate a new cadcraft `Layout`/`Viewport` at that sheet size and scale, title block included.

This is deliberately decoupled from the 1:1 modelling drawing: the model stays exact; the generated
fabrication sheet is a separate, disposable-and-regeneratable artifact optimized purely for shop
readability. The legibility threshold and the acceptable sheet-size range are configuration, not a
hardcoded constant — different shops/standards will want to tune it.

## 7. Explicitly out of scope for v1 (future sub-projects)

- Full parametric structural-element library (trusses, towers, auto-assembled connections) —
  fabcraft v1 stays in the "draw/import, then auto-dimension" flow; it does not model a whole
  structure from a few top-level parameters the way TecnoMETAL's macros do.
- Weld lists and connection tables specific to heavy structural steel — deferred to the "heavy
  structure" specialization sub-project.
- Sheet nesting (cutting-layout optimization across many parts) and direct CAM/NC (G-code) output —
  v1 exports per-part DXF suitable for cutting; nesting and machine-specific output are deferred to
  the "sheet metal/tube" specialization sub-project.
- Automatic Part-kind detection from true 3D models — blocked on cadcraft's 3D support, which is
  near 0% today. Until then, a 3D-drawn part without explicit Part data falls into the same
  single-question classification flow as 2D freehand geometry.

## 8. Testing and clean-room

- Follows cadcraft's "Prove it" standard: every dimension-placement rule, the flat-pattern/K-factor
  formula, and hostile inputs (a Part with zero holes, a hole touching the profile edge, zero
  thickness, a bend radius of zero) get a regression test.
- Flat-pattern/bend-allowance formulas and profile catalog dimensions come from public engineering
  standards and published manufacturer tables only — never from reading or copying a commercial
  CAD's bundled data or code.
- fabcraft never reads, disassembles, or copies code, icons, UI or file formats from TecnoMETAL or
  any other commercial product. Only observable behaviour/concept is used as a reference, exactly as
  cadcraft already does with AutoCAD.
